# 学习路线：先理解一条 claim 的完整流程

## 这次改了什么

入口仍是 `core/enterprise_evaluator.py`。原来写死的 PDF、代理和模型改成显式配置；
二分类改为支持、矛盾、证据不足；结果携带原文与位置；增加本地校验和离线测试。
旧脚本保留，先不用逐个学习。整个项目目前是可验证的工程原型，尚未证明模型准确率。

## 第一轮：运行和观察（约 30 分钟）

1. 按 README 创建虚拟环境、安装依赖、运行 dry-run。
2. 打开 `examples/reference.txt`、`examples/claims.md` 和输出 CSV。
3. 找到第一条 claim 对应的 `paragraph:1`；解释 similarity 为什么不是真实概率。
4. 确认 dry-run 的状态是 `NOT_EVALUATED`：这一步没有请模型判断。

完成标准：你能指出输入、输出、一次检索的证据来自哪里。

## 第二轮：按执行顺序阅读

| 顺序 | 函数/类 | 需要回答的问题 |
| --- | --- | --- |
| 1 | `main` | 哪些参数必填？错误如何退出？ |
| 2 | `ingest_document` / `Chunk` | 为什么空白页不能改变后续页码？ |
| 3 | `extract_claims` | 为什么一行包含多个断言可能有问题？ |
| 4 | `Retriever` | 为什么文档只 fit 一次、每条 claim 用 transform？ |
| 5 | `request_judgment` | 请求如何构造？哪些错误重试？ |
| 6 | `validate_judgment` | 引文真的存在，为什么判断仍可能错？ |
| 7 | `run` | 并发、错误隔离、CSV 保存如何连接？ |

每次读一个函数，自己说明输入、输出和一种失败情况，再看解释。

## 第三轮：三个独立改动

1. 增加一条改写句，先手写预期标签，再观察检索是否召回正确原文。
2. 增加一条“原文没说”的 claim，检查它是否被误判为矛盾。
3. 故意让模拟 API 返回伪造引文，解释测试为何拒绝它。

三种反例提醒：词很相似但含否定词；事实正确但文档没提；引文存在但不支持结论。
这些反例决定评测设计，不能靠把提示词写得更自信来解决。

## 后续验证与求职表述

真实 API 跑通后，另外收集人工核查的样本，分别记录：
证据召回是否成功、三个标签是否正确、重复运行是否一致、耗时和实际费用。
调提示词所用样本与最后报告的测试样本分开。初期样本少，应报告逐条结果，不包装成普遍准确率。

可以据实描述：Python + asyncio 的文档事实核查原型；TF-IDF 检索；证据追溯；
输出校验；可配置 API；离线回归测试。只有你实际运行、解释并修改过的部分才写成自己掌握的能力。
README 与核心流程有 AI 协助重构；学习时保留你独立完成的小改动及其验证记录。
